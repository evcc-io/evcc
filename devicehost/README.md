# Device host

A device host is an external process that provides device types to evcc. It is
set up once, tells evcc which types it can instantiate and which configuration
properties each type takes, and evcc then configures and instantiates devices
through it like any built-in device.

Unlike a template, the host does not ship YAML. It describes its properties as
structured data and evcc builds the template — and with it the configuration UI,
the defaults and the validation — from that description.

## Setup

```
evcc --device-host demo=127.0.0.1:8090
```

The flag is repeatable and takes `name=uri`. The name namespaces the host's
types, so `demo` offering a `pv` type registers the template `demo-pv`.

Hosts connect during `configureEnvironment` (`cmd/setup.go`), before devices are
configured, so their types are available to the regular device configuration.

## Protocol

gRPC, `devicehost/proto/devicehost.proto`:

| RPC | Purpose |
|-----|---------|
| `Types` | the device types this host provides, with their properties |
| `New` | instantiate a type from configuration properties, returns an id and the capabilities |
| `Call` | invoke a capability method on an instance |

### Types

Each type declares its class (`charger`, `meter`, …), a host-local type name and
its configuration properties:

```go
&pb.DeviceType{
    DeviceClass: "meter",
    Type:        "pv",
    Title:       "Example PV Meter",
    Properties: []*pb.Property{
        {Name: "uri", Title: "URI", Type: pb.PropertyType_PROPERTY_TYPE_STRING, Required: true},
        {Name: "scale", Title: "Scale", Type: pb.PropertyType_PROPERTY_TYPE_FLOAT, DefaultValue: "1", Advanced: true},
    },
}
```

A `Property` maps onto `templates.Param`: `name`, `type` (`STRING`, `BOOL`,
`INT`, `FLOAT`, `DURATION`, `CHOICE`), `title`, `help`, `required`, `mask` for
secrets, `advanced`, `default_value`, `example`, `unit` and `choice`.

evcc registers the resulting template and generates its render body, so the
device is configured through the normal path:

```yaml
type: devicehost
host: demo
device: pv
properties:
  uri: http://demo/pv
  scale: 2
```

Property values are yaml-quoted by the renderer, so secrets containing `:` or
`#` survive.

### New

`New` receives the class, the type and the configured properties. It returns an
opaque device id plus the api interfaces this particular instance supports:

```go
&pb.NewReply{Id: "pv-0", Capabilities: []string{"api.Meter", "api.MeterEnergy"}}
```

Capabilities are per instance, not per type — the same type may report different
capabilities depending on the hardware it finds.

### Call

Arguments and return values are json encoded; their Go types follow from the
capability's interface in `api/api.go`. A trailing `error` is not part of the
reply — return a gRPC error instead.

| Method | Args | Ret |
|--------|------|-----|
| `api.Meter.CurrentPower` | – | `[-3000.0]` |
| `api.PhaseCurrents.Currents` | – | `[10.0, 10.0, 10.0]` |
| `api.PhaseSwitcher.Phases1p3p` | `[1]` | – |

## Capabilities

`devicehost/capabilities.go` maps every api interface name to its decoration and
is generated by `cmd/implement` from the same interface list that produces
`api/implement/implementations.go`. Adding an interface there makes it available
over the wire — regenerate with `go generate ./...`.

Reported capabilities that evcc does not know are ignored, so a host may be
newer than the evcc it talks to.

## Implementing a host

Implement `pb.DeviceHostServer` and serve it over gRPC. `devicehost_test.go`
contains a complete example host with a pv meter and a wallbox, driven through
registration, instantiation and reading values.

## Limitations

* Transport is insecure and unauthenticated.
* A host that is unreachable at boot registers no types, so device configs
  referencing them fail to instantiate.
* The host name is the only namespace; two hosts configured under the same name
  collide.
* Devices are not re-instantiated when a host reconnects.
